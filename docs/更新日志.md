# cbhcli-jupyter 更新日志

## v0.2.11（2026-08-05）— 修复 nb_execute_cell "Canceled future" 报错

**问题**：`nb_execute_cell` 执行输出图片较多/较复杂的代码时，经常报 `Canceled future for execute_request message before replies were done`，agent 反复重试反复报错，用户看不到 cell 输出。
**根因**（三层）：
1. 前端 `_poll()` 用 `void this._runTask(task)` **fire-and-forget** 派发任务（不等待完成），而后端 `pending()` **每次轮询都返回全部未完成任务**。前端每 200ms 轮询一次，长任务（图片多=耗时长）在下次轮询时仍未回传 → 同一 task_id 被重复派发 N 次 → 同一 cell 被**并发执行多次**。
2. `OutputArea.execute` 设置 `output.future = future` 时（`set future`）会 **dispose 旧 future**（`@jupyterlab/outputarea` widget.js:223-226）。
3. 并发执行中后一次 dispose 前一次 future → 前一次 `future.done` reject "Canceled future" → 该次执行 `fail()` 回传 → agent 看到错误并重试 → 死循环。
**修复**（三管齐下）：
1. **后端 `nb_task_queue.py`**：`pending()` 改 **claim-once**——任务派发时打 `claimed_at` 标记，已派发的任务不再重复返回（前端崩溃未回传由 `wait()` 超时兜底）。
2. **前端 `nbClient.ts`**：`_poll()` 加 **in-flight 去重**（`_inflight` Set，已派发的 task_id 跳过），`_runTask` 完成后移除（双保险）。
3. **前端 `nbClient.ts`**：`_executeCellInPlace` 加**同 cell 执行中防护**——若 `cell.outputArea.future` 仍挂起，先等它收尾（最多 5s）再开始新执行，杜绝覆盖 dispose。
**验证**：CDP 直连后端任务队列模拟长任务（sleep 输出多图），轮询期间任务只派发一次、无重复执行、无 "Canceled future"，cell 输出区正常渲染。

## v0.2.10（2026-08-05）— 修复 notebook 工具 cell_type 参数不生效

**问题**：涉及 `cell_type` 的 notebook 工具均无法改类型——不能把 code cell 转成 markdown，也不能新增 markdown cell（默认 code 正常，但指定 markdown 无效）。
**根因**：前端 `nbClient.ts` 的 `_editCell`/`_insertCell` 用 `(cell.model.sharedModel as any).setCellType?.(...)` 改类型，但 **JupyterLab 4 的 `ICellSharedModel` 上根本没有 `setCellType` 方法**，可选链 `?.` 使其成为静默 no-op，且包在 try/catch 里吞掉，故"未生效"也无报错。后端 `nb_tools.py` 传参一直正常（`nb_edit_cell`/`nb_insert_cell` 都把 cell_type 放进 UI 任务 params）。
**修复**（仅 `nbClient.ts`）：新增 `_setCellType(nb, index, cellType)` 辅助方法，走**共享模型 `deleteCell + insertCell`**（对齐 JupyterLab `Private.changeCellType` 的内部实现，含 trusted 元数据处理、markdown 转未渲染），按 index 精确定位、不依赖选区、不打断用户当前选中状态；`_editCell`/`_insertCell` 改用它。`_insertCell` 的执行分支同时收紧为仅 code cell（避免对转换后的 markdown误执行）。
**验证**：CDP 直连 `__cbhcliNbClient` 实测 4 场景全过——新增 markdown cell、code→markdown、markdown→code、不传 cell_type 默认 code，内容转换后均保留。

## v0.2.4（2026-08-04）— 小眼睛严格模式：关闭时禁用全部 nb 工具

### 问题
小眼睛（选区上下文开关）此前只控制「是否把选区内容注入消息」。但 8 个 nb 工具在后端**始终注册**，
导致即便关掉小眼睛（没有选区上下文），agent 仍会**自主**调用 `nb_get_selection`/`nb_list_cells` 去翻
notebook、再用 `nb_edit_cell` 等改 cell——用户并未授权。

### 需求（用户确认：严格模式）
小眼睛关闭时，agent 不再使用任何 nb 工具（检索 + 修改），只做普通问答 + 非 nb 内置工具调用。
经确认采用**严格模式**：nb 工具仅在「注入了选区上下文」（小眼睛开 + 有选区）时启用；
其余情况（小眼睛关 / 无选区）一律禁用。

### 实现（前端传状态，后端按状态启停 nb 工具）
- **前端**：`streamChat` payload 新增 `nb_enabled` 字段（`api.ts`）；`chatPanel.ts` 发送时取
  `nbEnabled = payload !== display`（即「选区上下文是否真正注入」），随每条消息下发。
- **后端**：`chat_api.py` 新增 `set_nb_tools_enabled(cs, enabled)`——把 8 个 nb 工具名加入/移出
  注册表 `_disabled_tools`（只增删 nb，不影响 agent 配置里其他被禁工具）；`handlers.py` `ChatHandler`
  在 `_react_loop` 前读取 `body.get("nb_enabled", True)` 并应用（缺省 True 兼容旧客户端）。

### 机制（为何有效）
- `_react_loop` 开始时一次性 `get_openai_tools()` 生成工具 schema；禁用后 nb 工具**不在 schema**，
  LLM 根本看不到、无法发起调用。
- `ToolRegistry.execute()` 对禁用工具直接返回「已被禁用」错误 → 双保险（即便模型凭历史记忆硬调也被拒）。
- 系统提示本就不含 nb 工具列表（`NOTEBOOK_TOOLS_DOC` 仅定义未注入），无需改系统提示。

### 验证
- 单元（真实 ToolRegistry + NB_TOOLS）：禁用→schema 无 nb、execute 被拒；启用→恢复；反复切换幂等；不误动其他禁用工具。
- 集成（真实 WebChatSession）：会话 43 工具 → `nb_enabled=False` 剩 35（无 nb）→ `True` 恢复 43；send_file 仍移除。
- 打包 `cbhcli_jupyter-0.2.4-py3-none-any.whl` 安装，8899 运行 0.2.4。

### 行为说明
| 场景 | nb 工具 |
|------|---------|
| 小眼睛开 + 有选区（注入了选区上下文） | ✅ 启用 |
| 小眼睛关 | ⛔ 禁用（纯问答 + 非 nb 工具） |
| 无选区（眼睛不显示） | ⛔ 禁用（纯问答 + 非 nb 工具） |

## v0.2.2（2026-08-04）— 选区精确化 + 文件识别 + 渲染对齐 Web

新增前端渲染模块 `src/widgets/render.ts`（marked + 语法高亮 + 代码复制 + diff + ANSI 清理，移植自 cbhcli Web），并重写 `nbClient.ts` 选区/文件编辑器逻辑。

### 1. 选区显示列号 + 精确编辑
- 选区位置从 `L a-b` 细化为 `L a:c - b:d`（含列号），`SelectionContext` 新增 `startCol/endCol`。
- `nb_file_edit` 的 `selection_text` 分支改用编辑器当前选区**精确偏移**替换（不再 `indexOf`），行内有重复文本也不会改错位置（验证：`xxx` 只改选中那个）。

### 2. Markdown 渲染对齐 Web
- 改用 `marked`（新增依赖）渲染 AI 输出，支持 **表格**、代码块、列表、引用等。
- 代码块自动 **语法高亮**（monokai，移植 web 的 `highlightCode`）+ **复制按钮**（`enhanceCodeBlocks`）。

### 3. nb_file_read / nb_file_edit 识别非 ipynb 文件
- 根因：JupyterLab4 主区文件 widget 是 `FileEditorWidget extends DocumentWidget<FileEditor>`，
  编辑器在 `widget.content.editor`，旧代码误用 `widget.editor`（不存在）→ 非 ipynb 文件一律找不到。
- `_findFileEditor` 改用 `content.editor`，路径匹配支持 filename / 相对路径 / 绝对路径（绝对路径以 widget 相对路径结尾即匹配）。

### 4. 选区跟随最新活动编辑器（不再残留旧选区）
- `getCurrentSelectionContext` 重写优先级：当前聚焦文件编辑器 > notebook 活动 cell 文本选区 > 其余文件编辑器 > 整 cell 选中 > 兜底扫描。
- 修复"选了 cell1 再选 cell2 仍显示 cell1"：优先取**活动 cell** 的选区。

### 5. 选中任意 cell（空/非空）= 整 cell 内容
- `_notebookSelectedCells` 去掉"仅空 cell / 命令模式"限制：只要 cell 被选中即取全部内容；
  无选中 cell 时活动空 cell 仍视为选区（生成代码场景）。
- **关键根因（非空 cell 一度仍不识别）**：实测点击选中的 cell，`Notebook.isSelected(cell)` 返回
  `False`（编辑态/命令态都是），但 `Notebook.selectedCells` 数组**正确包含**该 cell。
  故改用 `content.selectedCells` 取选中 cell（`isSelected` 仅作兜底）。验证：空 cell / 非空 cell
  点击均识别为「cell N（整个代码块）」，且文本选区仍优先于整 cell。

### 6. edit/write/python 工具输出渲染对齐 Web
- `tool_confirm` 事件携带 `tool_args`，前端 `renderToolArgs` 按工具渲染：
  python→高亮代码块、edit→**diff 对比块**（行内字符级增删着色）、write→按文件类型高亮、terminal→bash 块。
- `tool_result` 用 `renderToolResult` 渲染输出（等宽块），保留上方参数。

### 7. python 输出 ANSI 乱码去除
- `stripAnsi()` 清理 `\x1b[36m` 等转义序列（python_tool.py 会给输出加颜色码），

## v0.2.1（2026-08-04）— 6 项体验修复

针对重构后反馈的 6 个问题逐一修复（前端 `nbClient.ts`/`chatPanel.ts`/`api.ts` + 后端 `handlers.py` + cbhcli `model.py`）。

### 1. Agent 工作路径跟随文件浏览器
- 现象：路径条显示对了，但 agent 工具（terminal/read/write）仍在服务器根目录工作。
- 根因：cbhcli 工具都基于进程 `os.getcwd()`，无 per-session cwd。
- 修复：新增后端 `POST /set_cwd`（把服务器进程 chdir 到文件浏览器目录）；`ChatHandler` 收到消息里的 `cwd` 也会 chdir；前端路径变化/发送时上报相对路径。

### 2. nb_edit_cell 选区精确匹配
- 现象：选中 `111111` 的后两个 1，edit 却改了前两个（`indexOf` 命中首个）。
- 修复：`_editCell` 优先用 cell 编辑器**当前选区的精确偏移**替换（新增 `_cellSelectionRange`），匹配不上才回退 `indexOf`。验证 `x = 111111` 选后两个 1 → `x = 111199`。

### 3. 空 cell / 命令模式选中 cell 的小眼睛识别
- 现象：选中空 cell（想让 agent 生成代码）小眼睛不出现。
- 根因：JupyterLab4 选择状态是 `Notebook.isSelected(cell)` 方法，`cell.isSelected` 属性不可靠；且空 cell 点击后进 edit 模式。
- 修复：`_notebookSelectedCells` 改用 `content.isSelected(cell)`；新增「活动 cell 为空即视为选区」（等待生成代码）。验证空 cell 2 识别为 `cell 2`。

### 4. notebook 执行输出显示在 cell 里
- 现象：agent 后台执行了代码，但 notebook cell 不显示输出。
- 根因：旧 `_executeCode` 用 `kernel.requestExecute` 直连内核，输出不回灌 cell 输出区。
- 修复：cell 执行改用 `OutputArea.execute(code, cell.outputArea, sessionContext)`（与 Shift+Enter 一致，实时渲染），完成后从 `outputArea.model` 提取输出回传 agent。验证 `print("hello world")` 输出出现在 cell。

### 5. 压缩按钮报错
- 现象：`ContextCompressor.compress() got an unexpected keyword argument 'instruction'`。
- 根因：cbhcli 的 `compress()` 参数名是 **`instructions`（复数）**。
- 修复：`ChatCompressHandler` 改传 `instructions=`。

### 6. JupyterLab 终端里 cbhcli 按 Ctrl+C 不能中断 ⭐（根因在 cbhcli，非插件）
- 现象：终端运行 cbhcli 问答时按 Ctrl+C 只显示 `^C` 不中断（Esc/Ctrl+C 都失效）。
- 排查：终端 SIGINT 送达正常（trap 能捕获）；终端用的是 `~/.local` cbhcli(5.1.8)，与插件(anaconda)分离。读 `/proc/<pid>/status` 发现**流式期间 `SigIgn` 含 SIGINT(bit2)**——SIGINT 被忽略；空闲 prompt 时 SIGINT 是被捕获的。进程内有 `tokio-rt-worker`/`sqlx-sqlite-wor` 线程，即 **chromadb 的 Rust/Tokio 内核**启动时把 SIGINT 置为 `SIG_IGN`。
- 修复（cbhcli `core/model.py`）：新增 `_ensure_sigint_handler()`，在 `chat_stream` 阻塞读取 `iter_lines()` 前若发现 SIGINT 被忽略则重置为 `signal.default_int_handler`。验证：流式中 Ctrl+C 出现「操作被中断」并回到 `❯` 提示符。
- 已重建 cbhcli-5.1.8 whl 并安装到 `~/.local`。

### 版本与打包
- cbhcli-jupyter 升到 **0.2.1**（pyproject.toml / package.json / handlers.py InfoHandler 三处）。
- 产出 `dist/cbhcli_jupyter-0.2.1-py3-none-any.whl`，已安装到 anaconda。
